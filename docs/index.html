NFC OUT-OF-BAND · BLE LEGACY PAIRING

从一次 NFC 触碰，到 BLE 灯控连接

遥控器从 NTAG 读取灯的 OOB 配对信息，直接建立 BLE 连接。随机数在 BLE 配对期间由两端分别生成并交换；STK 用于首次链路加密，LTK 留在设备中供 bond 使用。

01 / FLOW

系统流程

空白标签只在首次配置时写入 OOB 记录。之后触碰已配置标签，遥控器读取灯的地址和 TK，再由 BLE Security Manager 完成配对与加密。

阶段 01 · 首次配置

扫描灯的广播

遥控器发现名称为 NFC-BLE-LAMP 且提供服务 FFF0 的设备。

阶段 02 · NFC

写入 OOB NDEF

空 NTAG 保存灯地址、服务信息、角色和 TK；UID 不参与配对。

阶段 03 · 建链

读取并直连

触碰标签后校验记录，并使用其中的 BLE 地址发起连接。

阶段 04 · SMP

验证并生成 STK

交换 Confirm 和 Random；两端用共同 TK 算出相同的 STK。

阶段 05 · 控灯

Bond 后写 GATT

保存配对密钥，发现 FFF0 / FFF1 特征，按钮发送 toggle。

首次配对时的 SMP 消息顺序

遥控器 / Central 灯 / Peripheral

时序为首次 Legacy Pairing 的概念图。已存在 bond 时，BLE 栈可以使用保存的 LTK 恢复加密，不必每次重新生成 STK。

02 / RAND

随机数如何产生，又如何同步？

不是两台设备各自算出同一个随机数，而是各自产生一个随机数，再通过 SMP 交换这两个值。

两端分别生成自己的 RAND

遥控器是 Initiator，产生 RAND_I；灯是 Responder，产生 RAND_R。Legacy Pairing 使用 128 bit 随机值。项目应用代码不构造这些值，NimBLE Security Manager 在配对过程中处理生成和 SMP 消息。

先交换 Confirm，再公开 RAND

双方先用共同 TK、自己的 RAND 和本次配对参数计算 Confirm 并交换。之后 Central 发送 RAND_I，Peripheral 验证后发送 RAND_R。收到 RAND 后，各自重新计算对端的 Confirm；不匹配就终止配对。

用相同输入顺序算出 STK

两端最终都拥有同一对随机数和相同 TK。SMP 的 s1 对角色顺序固定，因此结果一致，作为首次链路加密的临时密钥。

STK = s1(TK, LP_RAND_R, LP_RAND_I)
NFC 标签不负责“同步”随机数

标签上的 TK 是 OOB 配对输入；它不会保存本次的 RAND_I、RAND_R、Confirm 或 STK。随机数只在这次 BLE SMP 交互中交换，下一次新配对会重新产生。

03 / KEYS

TK、STK、LTK 各自做什么

三种密钥位于配对流程的不同阶段，不能互相替代。

TK

Temporary Key

Legacy Pairing 的临时输入。OOB 方式让两端通过 NFC 取得同一个 TK，再用于计算 Confirm 和 STK。

本项目：固定开发值；存于固件并写进可读的 NDEF 标签。
STK

Short Term Key

由 TK 和这一轮的两个 RAND 经 s1 得出。用来开启首次 BLE 链路加密，并保护后续的密钥分发。

本项目：由 NimBLE 配对流程处理；不写进标签，也不作为长期 bond key 保存。
LTK

Long Term Key

bond 阶段使用的长期链路密钥材料。以后重新连接时，设备可使用已保存的 LTK 恢复链路加密。

本项目：通过 NimBLE bonding / ENC key distribution 保存到两端 NVS；不在 NFC 标签中。

固件启用 bonding，并在 NimBLE 配置中请求 ENC key distribution。具体密钥与关联参数的生成、交换和存储由 BLE 栈完成。

04 / NDEF

标签里有什么，什么不在里面

标签是一份 Bluetooth LE OOB NDEF 记录，作用是提供首次连接和 OOB 配对所需的信息。

NDEF 中的 OOB 字段

  • BLE 设备地址与地址类型
  • 设备名 NFC-BLE-LAMP
  • 服务 UUID 0xFFF0
  • LE Role 字段
  • LE Security Manager TK Value
  • Flags 与 NDEF / Type 2 TLV 封装

标签中没有

  • 本次配对的 RAND_I、RAND_R 和 Confirm
  • 计算出的 STK
  • Bond 保存的 LTK
  • 灯控特征 UUID 0xFFF1
  • 作为连接开关的 NFC UID
当前工程是开发配置，不适合直接用于生产安全场景

两份固件共享固定 TK，标签上的 NDEF 可被普通 NFC 读取和复制；同时 sm_sc = 0 选择的是 Legacy Pairing。即使日志报告 authenticated/bonded，也不代表这把公开的固定 TK 能抵抗标签复制或主动攻击。量产应为每台灯生成独立随机 TK，保护密钥配置与标签写入过程，并重新评估配对安全模式。

05 / DEVICE

项目中的硬件与控制命令

配对成功后，遥控器发现灯的 GATT 控制特征，并用写入命令驱动 RGB LED。

PN532 I²C SDA GPIO4 · SCL GPIO5 · IRQ GPIO6 · RESET GPIO7 按钮 GPIO9 · 低电平有效 RGB LED GPIO48 GATT Service FFF0 · Characteristic FFF1

控制特征的单字节命令

  • 0：灯灭
  • 1：灯亮
  • 2：切换当前状态；GPIO9 按钮发送此命令

灯端校验

  • 命令写入要求连接已加密
  • 还要求 authenticated 与 bonded 状态
  • 灯端 WS2812 RGB LED 由 GPIO48 输出驱动
